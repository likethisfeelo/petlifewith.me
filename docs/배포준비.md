# 배포 준비 — AWS 계정·CLI·도메인·서브도메인

현재 상태: 도메인(petlifewith.me) 구매, ACM 인증서 발급(us-east-1, ARN 은 `sst.config.ts`),
IAM 사용자·CLI 프로필(`petlife`) 설정 완료.
이 문서는 **배포 전 준비**를 다룬다. 실제 배포(OpenNext/SST)는 `docs/배포.md` 의 스크립트로 한다.

> **절대 규칙**: 액세스 키를 채팅·메일·커밋 어디에도 붙여넣지 않는다. 키는 로컬
> `aws configure` 로만 저장한다 (`C:\Users\<사용자>\.aws\credentials`). 이 파일도 커밋 금지.

## 1. 로컬 설치 체크리스트

| 항목 | 확인 명령 | 없으면 |
|---|---|---|
| 기존 필수 (이미 있음) | `node --version` `pnpm --version` `docker --version` `git --version` | docs/운영.md 0장 |
| **AWS CLI v2** (신규) | `aws --version` → `aws-cli/2.x` | `winget install Amazon.AWSCLI` 후 PowerShell 새 창 |

**아직 설치하지 않는 것**: CDK / SST / OpenNext / Terraform — 배포 단계에서 방식 확정 후 추가한다
(claude.md 10-8: 인프라를 미리 세우면 쓰지 않는 리소스에 비용이 나간다).

## 2. AWS CLI — 새 IAM 사용자를 named profile 로

기존에 쓰던 사용자와 섞이지 않게 **named profile** 을 쓴다. 프로필 이름은 `petlife` 로 통일.

```powershell
# 1) 프로필 등록 (IAM 콘솔에서 만든 액세스 키 입력)
aws configure --profile petlife
#   AWS Access Key ID     : (입력)
#   AWS Secret Access Key : (입력)
#   Default region name   : ap-northeast-2
#   Default output format : json

# 2) 누구로 잡혔는지 확인 — Account/Arn 이 새 사용자·새 계정인지 본다
aws sts get-caller-identity --profile petlife

# 3) 프로필 목록 (기존 사용자와 분리 확인)
aws configure list-profiles
```

이 프로젝트 작업을 할 때만 기본 프로필로 쓰려면:

```powershell
$env:AWS_PROFILE = "petlife"     # 지금 PowerShell 창에서만 유효 — 권장
# setx AWS_PROFILE petlife       # 영구 설정. 기존 사용자로 하는 다른 작업과 충돌하면 쓰지 말 것
```

`--profile petlife` 를 매번 붙이는 쪽이 실수 없이 가장 안전하다.

**스크립트로 한 번에** — 프로필 목록·활성 프로필·실제 자격 증명(계정/ARN)·리전을 확인하고,
검증에 성공한 경우에만 전환한다. 프로젝트 계정(인증서 ARN 의 계정)과 다르면 경고한다:

```powershell
.\scripts\aws-profile.ps1                    # 현재 상태 확인
.\scripts\aws-profile.ps1 -All               # 모든 프로필의 자격 증명까지 확인
.\scripts\aws-profile.ps1 -Use petlife       # 이 창을 petlife 프로필로 전환 (STS 검증 후)
.\scripts\aws-profile.ps1 -Use petlife -Persist   # 새 창에도 영구 적용 (충돌 주의)
.\scripts\aws-profile.ps1 -Clear             # 전환 해제 (-Persist 를 붙이면 영구 설정도 제거)
```

### 권한·보안 메모

- IAM 사용자에 **MFA** 를 켠다 (콘솔 로그인용).
- 배포 단계에서 필요한 권한: CloudFront, Lambda, S3, Route 53, ACM(읽기), CloudWatch Logs,
  IAM(역할 생성·PassRole). 정책을 좁히기 어려우면 초기에는 관리자 권한으로 시작하고
  배포 방식 확정 후 최소 권한으로 줄인다.
- 액세스 키는 90일 주기로 회전. 안 쓰는 키는 즉시 비활성화.

## 3. 도메인·인증서 검증

```powershell
# Route 53 호스티드 존 확인 (petlifewith.me 가 있어야 한다)
aws route53 list-hosted-zones --profile petlife

# 인증서 확인 — 두 리전 모두 조회해 본다
aws acm list-certificates --region us-east-1 --profile petlife
aws acm list-certificates --region ap-northeast-2 --profile petlife
```

**중요 — 인증서 리전** (claude.md 10 에도 명시):

- **CloudFront 에 붙는 인증서는 반드시 us-east-1** 이어야 한다. 서울(ap-northeast-2)에서
  발급했다면 CloudFront 에는 쓸 수 없다 — us-east-1 에서 다시 발급한다 (무료, DNS 검증).
- 도메인 범위는 **`petlifewith.me` + `*.petlifewith.me`** 두 개를 한 인증서에 담는 것을 권장.
  와일드카드 하나로 dev/admin/service/product 서브도메인이 전부 커버된다.
- 상태가 `ISSUED` 인지 확인. `PENDING_VALIDATION` 이면 ACM 콘솔의 "Route 53에서 레코드 생성"
  버튼으로 검증 레코드를 넣는다.

## 4. 도메인 구조 (확정)

| 호스트 | 용도 | 앱에서의 실체 |
|---|---|---|
| `petlifewith.me` | 메인 서비스 (콘텐츠 + 디렉토리) | 앱 그대로 |
| `admin.petlifewith.me` | 전체 관리자 (블로그 글 포함) | `/admin` 으로 호스트 라우팅 |
| `service.petlifewith.me` | 업체 정보 — 사장님용 | `/portal/spot` 으로 호스트 라우팅 |
| `product.petlifewith.me` | 제품·브랜드 등록 — 사장님용 | `/portal/product` 로 호스트 라우팅 |
| `dev.petlifewith.me` | 개발(스테이징) 배포 | **별도 스택** + `NEXT_PUBLIC_SITE_ENV=preview` |

- 호스트 라우팅은 `web/src/middleware.ts` + `web/src/lib/hosts.ts` 에 이미 구현되어 있다.
  admin/service/product 는 **같은 앱, 같은 배포**에서 호스트로 갈라진다 — CloudFront 배포 하나에
  Alternate domain name 4개(메인 + 3개)를 걸면 된다. dev 만 별도 배포다.
- **기획서의 "지역별 서브도메인 금지"(SECTION 01)와 충돌하지 않는다.** 그 결정은 콘텐츠 SEO
  이야기이고, 지역 URL 은 계속 `/spot/[시도]/[시군구]` 서브폴더다. 여기 서브도메인은 운영용
  기능 분리다. admin·portal 페이지는 전부 noindex 라 검색 권위 분산도 없다.
- `dev.` 배포에는 반드시 `NEXT_PUBLIC_SITE_ENV=preview` — 실도메인이어도 robots 차단 +
  전 페이지 noindex 가드가 걸린다 (`web/src/lib/config.ts` siteEnv).

### 로컬에서 서브도메인 미리 보기

브라우저는 `*.localhost` 를 자동으로 127.0.0.1 로 해석한다. hosts 파일 수정 없이:

```
http://admin.localhost:3000     → 관리자
http://service.localhost:3000   → 업체 사장님 페이지
http://product.localhost:3000   → 제품·브랜드 사장님 페이지
```

## 5. DNS 레코드 계획 (배포 단계에서 생성)

지금 만들 필요 없다 — CloudFront 배포가 생겨야 대상이 나온다. 계획만 적어둔다.

| 레코드 | 타입 | 값 |
|---|---|---|
| `petlifewith.me` | A (Alias) | 메인 CloudFront 배포 |
| `www.petlifewith.me` | A (Alias) | 메인 CloudFront 배포 (앱이 www → apex 취급) |
| `admin` / `service` / `product` | A (Alias) | 메인 CloudFront 배포 (같은 배포) |
| `dev.petlifewith.me` | A (Alias) | dev 전용 CloudFront 배포 |

## 6. 다음 단계 — 배포 (방식 확정됨)

배포 방식은 **SST v4 (OpenNext)** 로 확정. 정의는 루트 `sst.config.ts`,
절차·스크립트·비용·트러블슈팅은 **`docs/배포.md`** 를 따른다. 요약:

```powershell
.\scripts\aws-db.ps1 -DevFixtures    # 한 번: RDS + env 파일 + 마이그레이션·시드
.\scripts\deploy.ps1 -Stage dev      # dev 먼저
.\scripts\deploy.ps1 -Stage prod     # 검증 후 운영
```

DNS 레코드(5장 표)는 배포가 Route 53 에 자동 생성하므로 손으로 만들지 않는다.
