# 배포 — AWS (OpenNext/SST) 런북

배포 방식 확정: **SST v4 (OpenNext)**. 정의는 루트 `sst.config.ts`, 실행은 `scripts/*.ps1`.
모든 스크립트는 **중간 확인(y/n)을 묻지 않는다** — 위험한 것(철거)은 스위치를 명시해야만 동작한다.
사전 준비(계정·프로필·인증서 검증)는 `docs/배포준비.md`.

## 0. 구성 (무엇이 어디에 뜨나)

```
사용자 ─ CloudFront (인증서: us-east-1 와일드카드)
          ├─ 정적 자산 ─ S3 (앱 자산 + ISR 캐시, SST 관리)
          └─ SSR/ISR ─ Lambda ap-northeast-2 (OpenNext 서버, arm64, node22)
                          └─ RDS PostgreSQL 16 (petlife-db, 퍼블릭 엔드포인트 + TLS)
미디어 업로드 ─ presigned PUT → 미디어 S3 버킷(공개 읽기, SST 관리)
DNS ─ Route 53 (배포가 레코드 자동 생성)
```

- **스테이지 2개**: `prod`(petlifewith.me + www/admin/service/product 별칭 — 같은 배포 하나,
  호스트 라우팅은 앱 미들웨어) / `dev`(dev.petlifewith.me, `preview` → 전면 noindex).
- **dev 의 기능 서브도메인은 하이픈 연결**: `admin-dev.` `service-dev.` `product-dev.petlifewith.me`.
  `admin.dev.…` 는 2단계라 와일드카드 인증서(`*.petlifewith.me`)가 커버하지 못해서다.
  운영과 매핑은 동일하다 (admin→`/admin`, service→`/portal/spot`, product→`/portal/product`).
- **RDS 는 SST 밖**이다. 상태를 가진 리소스를 IaC 에 넣으면 `sst remove` 실수 한 번에
  데이터가 날아간다. DB 는 `scripts/aws-db.ps1` 이 CLI 로 만들고 삭제 보호를 켠다.
- 인스턴스 하나(db.t4g.micro)에 `app_prod` / `app_dev` 두 데이터베이스를 둔다.
- ISR 재검증 큐·캐시·이미지 함수는 SST 가 OpenNext 규격대로 자동 구성한다 (claude.md 10-4).

## 1. 스크립트

| 스크립트 | 용도 | 주요 옵션 |
|---|---|---|
| `scripts/aws-profile.ps1` | AWS 프로필 확인·전환 (계정 검증 포함) | `-Use petlife`, `-All`, `-Clear`, `-Persist` |
| `scripts/aws-db.ps1` | RDS 생성 + app_prod/app_dev + `.env.deploy.*` 생성 + 마이그레이션·시드. 재실행 안전 | `-DevFixtures`, `-SkipSeed` |
| `scripts/deploy.ps1` | 프리플라이트 → 설치·타입체크·테스트 → 마이그레이션 → `sst deploy` | `-Stage dev\|prod`, `-SkipTests`, `-SkipPreflight`, `-SkipMigrate` |
| `scripts/aws-destroy.ps1` | 스테이지 철거. `-Yes` 없이는 거부, prod 는 `-Force` 추가 + sst.config.ts 보호 해제까지 필요 | `-Stage`, `-Yes`, `-Force` |
| `scripts/aws-logs.ps1` | 배포된 Lambda 의 최근 로그 — 5xx 원인 확인 | `-Stage`, `-Minutes`, `-ErrorsOnly` |
| `scripts/db.ps1` | 배포 DB(또는 로컬)에 마이그레이션·기준 시드·적재 현황 — 배포 없이 DB 만 맞출 때 | `-Stage dev\|prod`, `-Task migrate\|seed\|status\|all` |

`deploy.ps1` 은 마이그레이션과 함께 **기준 시드(seed:base — 토픽·스팟 유형·지역)** 를 매번 실행한다
(멱등 upsert). 콘텐츠 시드는 관리자 수정을 덮어쓰므로 자동 실행하지 않는다.

## 1-1. 배포 실행은 GitHub Actions (표준 경로)

**Windows 에서 `sst deploy` 를 직접 돌리면 안 된다** — OpenNext 가 Windows 빌드를 지원하지
않아 서버 번들에 node_modules 가 빠지고, Lambda 가 `Cannot find package 'next'` 로 전부
502 가 된다 (2026-08-25 dev 배포에서 실증). `deploy.ps1` 은 Windows 에서 이를 감지하고
거부한다(`-AllowWindowsBuild` 로만 우회). 그래서 배포는 **GitHub Actions(리눅스 러너)** 가 표준이다:
`.github/workflows/deploy.yml`.

**최초 1회 설정** — GitHub 저장소 → Settings → Secrets and variables → Actions →
New repository secret 로 3개(운영 배포 전엔 4번째까지) 등록:

| Secret 이름 | 값 |
|---|---|
| `AWS_ACCESS_KEY_ID` | petlife IAM 사용자 액세스 키 ID |
| `AWS_SECRET_ACCESS_KEY` | 같은 사용자의 시크릿 키 |
| `ENV_DEPLOY_DEV` | 로컬 `.env.deploy.dev` **파일 내용 전체** |
| `ENV_DEPLOY_PROD` | (운영 배포 시) `.env.deploy.prod` 내용 전체 |

키 값은 로컬 `C:\Users\<사용자>\.aws\credentials` 의 `[petlife]` 섹션에 있고, env 파일은
`Get-Content .env.deploy.dev -Raw | Set-Clipboard` 로 복사하면 된다.
**GitHub Secrets 화면에만 붙여넣는다** — 채팅·커밋·이슈에는 절대 금지.

**실행**: Actions 탭 → `deploy` → Run workflow → 브랜치·stage 선택 → Run.
워크플로가 설치→타입체크·테스트→마이그레이션+기준 시드→`sst deploy` 를 순서대로 한다.

주의: workflow_dispatch 버튼은 **워크플로 파일이 기본 브랜치(main)에 있어야** Actions 탭에
보인다. 작업 브랜치에만 있으면 먼저 main 에 머지한다.

`deploy.ps1` 은 WSL/리눅스(및 프리플라이트·마이그레이션 등 배포 전 점검)용으로 남는다.

## 2. 처음 배포 (딱 한 번)

```powershell
# 0) 프로필이 새 IAM 사용자(프로젝트 계정)인지 확인
.\scripts\aws-profile.ps1

# 1) DB 준비 — RDS 생성(5~10분 대기), env 파일 생성, 마이그레이션+시드
.\scripts\aws-db.ps1 -DevFixtures        # dev 에만 샘플 데이터 포함
```

2. **GitHub Actions 시크릿 등록** (1-1장, 최초 1회) 후
   Actions → `deploy` → Run workflow → stage `dev` (첫 배포는 CloudFront 생성 때문에 10~15분)
3. dev 검증(아래 3-1) 후 같은 방법으로 stage `prod`

### 3-1. dev 검증 체크리스트

- `https://dev.petlifewith.me` 홈이 뜬다. `robots.txt` 가 전체 차단(preview)인지 본다.
- 서브도메인 3종이 뜬다: `admin-dev.petlifewith.me`(관리자 — 운영의 admin. 과 동일 매핑),
  `service-dev.` / `product-dev.`(사장님 포털). 경로 접근(`dev.petlifewith.me/admin`)도 그대로 된다.
- 관리자 로그인 — 토큰은 `.env.deploy.dev` 의 `ADMIN_TOKEN`.
- `admin-dev.` 에서 이미지 업로드 1건 → 게시글 히어로로 지정 → 페이지에 보이면 미디어 버킷·CORS 정상.
- 게시글 저장 → 몇 분 내 반영(ISR)되는지 확인.

### 3-2. prod 배포 (dev 검증이 끝난 뒤)

**prod 는 `NEXT_PUBLIC_SITE_ENV=production` 이라 검색에 색인된다.** 빈 페이지가 먼저 크롤되지
않도록 **데이터를 먼저 넣고 배포**한다. dev DB(app_dev)와 prod DB(app_prod)는 별개라
dev 에 적재한 인허가 데이터가 prod 에 자동으로 오지 않는다.

```powershell
# 1) prod DB 스키마·기준 시드 (배포 없이) + 현재 상태 확인
.\scripts\db.ps1 -Stage prod

# 2) 인허가 CSV 5종을 prod DB 로 적재 (dev 와 같은 명령, -Stage prod 만 다르다)
.\scripts\etl.ps1 -Stage prod -Dataset animal-pharmacy       -File "data\raw\동물_동물약국.csv"             -Encoding cp949 -ReferenceDate 2026-08-25
.\scripts\etl.ps1 -Stage prod -Dataset animal-beauty         -File "data\raw\동물_동물미용업.csv"           -Encoding cp949 -ReferenceDate 2026-08-25
.\scripts\etl.ps1 -Stage prod -Dataset animal-transport      -File "data\raw\동물_동물운송업.csv"           -Encoding cp949 -ReferenceDate 2026-08-25
.\scripts\etl.ps1 -Stage prod -Dataset animal-drug-wholesale -File "data\raw\동물_동물용의약품도매상.csv"   -Encoding cp949 -ReferenceDate 2026-08-25
.\scripts\etl.ps1 -Stage prod -Dataset animal-medical-device -File "data\raw\동물_동물용의료용구판매업.csv" -Encoding cp949 -ReferenceDate 2026-08-25

# 3) 적재 확인 (dev 와 같은 수치가 나와야 한다)
.\scripts\db.ps1 -Stage prod -Task status
```

4. **`ENV_DEPLOY_PROD` 시크릿 등록** — `Get-Content .env.deploy.prod -Raw | Set-Clipboard` 로
   복사해 GitHub Settings → Secrets and variables → Actions 에 붙여넣는다.
   dev 내용을 잘못 넣으면 워크플로가 `app_dev` 를 감지해 배포를 거부한다.
5. **Actions → deploy → Run workflow → stage `prod`** (첫 배포는 CloudFront 생성 때문에 10~15분)

### 3-3. prod 배포 후 (런칭 절차)

1. `https://petlifewith.me` + `admin.` `service.` `product.` `www.` 확인 (DNS 전파 수 분).
   `robots.txt` 가 **차단이 아니어야** 한다 (dev 와 반대 — production 은 색인 허용).
2. 관리자 로그인 토큰은 `.env.deploy.prod` 의 `ADMIN_TOKEN` — dev 와 다른 값이다.
3. 기본 OG 이미지: 관리자 미디어에 1200x630 업로드 → 공개 URL 을
   `.env.deploy.prod` 의 `NEXT_PUBLIC_DEFAULT_OG_IMAGE_URL` 에 넣고 시크릿 갱신 후 재배포.
4. Google Search Console·네이버 서치어드바이저 등록, 사이트맵 `https://petlifewith.me/sitemap.xml` 제출.
5. 쿠팡 파트너스 실링크 연동 (기획서 SECTION 07, 고지는 자동 렌더).

## 3. 평시 배포 (코드가 바뀌었을 때)

GitHub Actions → `deploy` → Run workflow → `dev` 로 먼저, 확인 후 `prod`.
(WSL/리눅스에서는 `.\scripts\deploy.ps1 -Stage dev|prod` 도 동일하게 동작한다.)

- **콘텐츠·업체 등록은 재배포가 필요 없다** — DB 에 저장되고 ISR 주기(`web/src/lib/revalidate.ts`)로 반영된다.
- 스키마 변경 시에도 순서는 같다: `deploy.ps1` 이 배포 전에 마이그레이션을 먼저 실행한다.
- ETL(인허가 CSV 적재)은 로컬에서 배포 DB 로 직접 실행한다 — `-Stage` 가 `.env.deploy.<stage>` 의
  DATABASE_URL 을 자동으로 쓴다:
  ```powershell
  .\scripts\db.ps1 -Stage prod                # 스키마·기준 시드 먼저 (배포 없이)
  .\scripts\etl.ps1 -Stage prod -Dataset animal-beauty -File data\raw\beauty.csv -Encoding cp949 -ReferenceDate 2026-08-01
  .\scripts\db.ps1 -Stage prod -Task status   # 적재 확인
  ```

## 4. `.env.deploy.<stage>` (커밋 금지, 분실 주의)

`aws-db.ps1` 이 생성한다. `.env.*` 는 gitignore 대상이라 커밋되지 않는다 — **비밀번호 관리자 등에 백업**해 둘 것.
분실 시 `aws-db.ps1` 재실행이 마스터 비밀번호를 리셋해 복구한다.

| 키 | 값 |
|---|---|
| `DATABASE_URL` | `postgresql://app_admin:...@petlife-db...:5432/app_prod?sslmode=no-verify` |
| `ADMIN_TOKEN` / `AUTH_SECRET` | 스테이지별 무작위 생성 (로컬 값과 다르다) |
| `NEXT_PUBLIC_CONTACT_EMAIL` 등 | 선택 — 주석 해제 후 값 입력, 재배포로 반영 |

`NEXT_PUBLIC_SITE_URL`·`SITE_ENV`·스토리지 설정은 파일에 넣어도 **무시된다** — `sst.config.ts` 가
스테이지별로 고정 주입한다 (dev 에 preview 누락 같은 사고 방지).

## 6. 보안 트레이드오프 (지금 상태와 강화 경로)

지금 구조는 **운영 단순함**을 골랐다. 어떤 대가인지 명시한다.

- **RDS 퍼블릭 엔드포인트 + 보안그룹 5432 전체 개방**: Lambda 를 VPC 밖에 두어
  NAT 게이트웨이 비용(월 $32+)을 피하고, 로컬 ETL·마이그레이션이 바로 접속하기 위함.
  방어선은 강한 무작위 비밀번호(32자) + TLS + 삭제 보호다.
- **`sslmode=no-verify`**: 전송은 암호화되지만 서버 인증서 CA 검증은 생략한다
  (Node 신뢰 저장소에 RDS CA 가 없어서). 강화하려면 RDS 글로벌 CA 번들을 앱에 포함하고
  `verify-full` 로 바꾼다.
- **강화 경로(트래픽·팀이 커지면)**: Lambda 를 VPC 에 넣고 RDS Proxy + 보안그룹 축소,
  시크릿을 Secrets Manager 로 이전(`web/src/lib/config.ts` 한 곳 교체 — claude.md 10-3),
  미디어 버킷 앞에 CloudFront(`NEXT_PUBLIC_ASSET_BASE_URL` 교체만으로 전환 — DB 는 오브젝트 키만 저장).
- 인증서 ARN(us-east-1)·계정 ID 는 자격 증명이 아니라 식별자다 — 리포에 있어도 된다.
  **액세스 키는 어디에도 커밋·붙여넣기 금지** (배포준비.md 절대 규칙).

## 7. 트러블슈팅

| 증상 | 원인·조치 |
|---|---|
| **모든 경로가 502 + "Internal Server Error" 텍스트** (favicon 까지) | 서버 Lambda 실패. `.\scripts\aws-logs.ps1 -Stage dev -ErrorsOnly` 로 확인. **실증된 원인: Windows 에서 만든 OpenNext 번들** — 로그에 `Cannot find package 'next'` 가 찍힌다. 해결: GitHub Actions 로 재배포 (1-1장) |
| 페이지가 아주 느리거나 504 | Lambda→RDS 접속 실패 반복. 보안그룹 5432 개방·DATABASE_URL 확인. 접속 실패는 8초 안에 500 으로 떨어지게 되어 있다(pg connectionTimeoutMillis) |
| `Certificate status is PENDING_VALIDATION` | ACM 콘솔(us-east-1)에서 "Route 53에서 레코드 생성"으로 DNS 검증 |
| `Certificate must cover ...` | 서울 리전 인증서를 넘겼거나 와일드카드 누락 — us-east-1 에서 `petlifewith.me`+`*.petlifewith.me` 로 재발급 후 ARN 교체(`$env:CERT_ARN` 또는 sst.config.ts) |
| `.env.deploy.dev 가 없습니다` | `.\scripts\aws-db.ps1` 먼저 |
| `sst deploy` 중간 실패 | 그대로 다시 실행 — SST 는 상태 기반이라 이어서 배포한다 |
| 도메인이 안 열림 (배포 직후) | DNS 전파 대기 수 분. `nslookup petlifewith.me` 로 확인 |
| 사이트는 뜨는데 DB 데이터가 안 보임 | Lambda→RDS 접속 실패. 보안그룹 5432 개방 여부, `.env.deploy.*` 의 DATABASE_URL 확인 |
| 업로드 실패 (CORS) | 관리자에 접속한 호스트가 버킷 CORS 허용 목록에 있는지 — prod 는 admin.petlifewith.me, dev 는 admin-dev.petlifewith.me 에서 업로드 |
| dev 가 구글에 안 잡힘 | 정상. dev 는 preview 로 전면 noindex 다 |
| 롤백 | `git checkout <이전 커밋>` 후 `.\scripts\deploy.ps1 -Stage prod` (DB 스키마 롤백은 별도 판단) |

## 8. 철거

```powershell
.\scripts\aws-destroy.ps1 -Stage dev -Yes    # dev 스택 제거 (RDS 는 남는다)
```

prod 는 `sst.config.ts` 의 `protect`/`removal: retain` 때문에 스크립트+`-Force` 로도 바로 지워지지
않는다 — 정말 내릴 때만 설정을 고쳐서 진행한다. RDS 삭제 명령은 스크립트가 출력만 하고 실행하지 않는다.
